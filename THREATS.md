# TrustVault Threat Model

## 1. Project Overview
TrustVault is a Django-based secure document-sharing application with role-based access control and an audit trail.

## 2. Assets to Protect
- User accounts and authentication sessions
- Uploaded documents and document metadata
- Document ownership and sharing permissions
- Audit logs and integrity hashes
- Application configuration and credentials

## 3. Security Threats and Mitigations

### Threat 1: Unauthorized Document Access
**Threat:** A user may try to access another user's document by changing its URL or document ID.

**Mitigation:** Check authorization on the server for every document request. Only owners and users with valid grants should receive access.

**Verification:** Test access attempts by unrelated users and users whose grants have been revoked.

### Threat 2: Permission Escalation
**Threat:** A viewer may attempt to edit, share, revoke, or delete a document without permission.

**Mitigation:** Enforce role, ownership, and grant checks on every relevant server-side endpoint.

**Verification:** Add tests for each prohibited operation.

### Threat 3: Access After Revocation
**Threat:** A user may retain access after the document owner revokes their grant.

**Mitigation:** Check the current grant status on every request.

**Verification:** Confirm that access is denied immediately after revocation.

### Threat 4: Audit Log Tampering
**Threat:** Someone with database write access may modify or delete audit events.

**Mitigation:** Use hash-linked audit events and verify the integrity of the chain. Restrict audit-log access to administrators.

**Limitation:** A hash chain stored in the same writable database is not fully tamper-proof. An attacker who can rewrite all records and recompute hashes may be able to replace the chain.

### Threat 5: Missing Audit Events
**Threat:** Important actions or denied access attempts may not be recorded.

**Mitigation:** Log document uploads, downloads, edits, deletions, permission changes, and denied access attempts.

**Verification:** Test the audit event generated by each operation and failure path.

### Threat 6: Malicious or Oversized Uploads
**Threat:** An attacker may upload unsafe files or files that exceed resource limits.

**Mitigation:** Validate permitted file types and file sizes. Store uploaded files privately and serve them through authorized views.

**Verification:** Test invalid file types and oversized uploads.

### Threat 7: Secret Exposure
**Threat:** Passwords, API keys, or secret configuration may be published in the Git repository.

**Mitigation:** Keep secrets in environment variables, exclude secret files from Git, and inspect staged files before committing.

### Threat 8: Cross-Site Scripting
**Threat:** Malicious document metadata may be rendered as executable HTML or JavaScript.

**Mitigation:** Use Django template autoescaping, validate input, and avoid unsafe HTML rendering.

### Threat 9: Cross-Site Request Forgery
**Threat:** A malicious website may attempt to trigger actions using an authenticated user's session.

**Mitigation:** Keep Django CSRF protection enabled and protect state-changing form submissions.

## 4. Accepted Risks and Limitations
- A hash chain alone cannot guarantee protection against an attacker who can rewrite the entire database.
- SQLite development settings are not automatically suitable for production.
- File validation reduces upload risks but cannot guarantee that every file is safe.
- Production deployment requires secure configuration, HTTPS, protected credentials, and appropriate backups.

## 5. Security Test Checklist
- [ ] Unauthorized users cannot read other users' documents.
- [ ] Viewers cannot perform unauthorized edits or sharing actions.
- [ ] Revoked grants immediately stop granting access.
- [ ] Sensitive successful actions and denied attempts are audited.
- [ ] Tampered audit records and broken hash links are detected.
- [ ] Invalid and oversized uploads are rejected.
- [ ] Non-admin users cannot view the audit log.

## 6. Review Status
This document records threats, proposed mitigations, and tests that need verification. Do not mark a security requirement as verified until the implementation and corresponding tests have been checked.
